# Проверка занятий преподавателем

Реализация от 20 октября 2026 года. Владелец применил миграцию рабочей базы и подтвердил назначение преподавателя скриншотами Supabase. Сам GitHub Pages не применяет SQL. После развёртывания выполняется проверка авторизованного кабинета на сайте; инструкции ниже сохраняются для новой установки.

## Что входит

- `/teacher/` — кабинет преподавателя; `/teacher/?view=student` — занятия ученика.
- Преподаватель видит список подключённых учеников, занятия, первые и последние ответы, исправления, до 20 последних повторов каждого задания и собственные предложения.
- Первый ответ и суммарные счётчики повторов не теряются при ограничении списка повторов. Новая попытка получает новый UUID и не удаляет прежние отчёты.
- Сохранить можно незавершённое занятие. Запросы группируются: после пяти проверенных ответов, через 20 секунд после изменения, при открытии результата или по кнопке. Нет постоянного опроса и запросов на каждый клик. Статус явно различает устройство и облако.
- Комментарии, исправленные варианты и отметка «Отработано на занятии» сохраняются преподавателем отдельно. Они доступны ученику в «Моих занятиях».
- «Продолжить занятие» восстанавливает попытку; «Повторить ошибки» открывает ошибки первого ответа, включая уже исправленные, для закрепления. Это продолжение исходной попытки с сохранением первого результата. «Пройти заново» начинает отдельную попытку.
- Для незарегистрированного ученика есть перенос гостевой попытки явной кнопкой после входа. Кнопка подтверждает принадлежность ответов ученику; занятие другого человека автоматически не присваивается. При наличии текущей личной работы она сначала сохраняется. Данные на другом устройстве не появляются, пока их не отправили с исходного браузера.

## Установка базы

1. В Supabase того же проекта, который указан в `clase/supabase-config.js`, выполнить `supabase/teacher-reports.sql` от владельца базы. Скрипт транзакционный и повторно применимый; старые `profiles`, `lesson_attempts`, A1-прогресс не изменяет.
2. Проверить email **существующего подтверждённого аккаунта преподавателя**. Только после идентификации выполнить от владельца базы (подставить его email и имя):

```sql
insert into public.teaching_teachers(user_id, display_name)
select id, 'Имя преподавателя'
from auth.users
where lower(email) = lower('VERIFIED_TEACHER_EMAIL')
  and email_confirmed_at is not null
on conflict (user_id) do update
set display_name = excluded.display_name;
```

Запрос должен затронуть ровно один аккаунт. Привилегия не берётся из `profiles.role` и не назначается через браузер. Service-role ключи не нужны на сайте.

3. Проверить регистрацию и вход из `/clase/` и `/teacher/`. Email Redirect URLs в Supabase Auth должны разрешать `https://esprofe.es/clase/` и `https://esprofe.es/teacher/`. Подтверждение email не отключать.
4. Преподаватель создаёт приглашение. Одноразовый случайный код действует семь дней и предназначен для одного ученика. Передаёт код сам преподаватель.
5. Ученик входит в «Мои занятия», вводит код и своё имя и подтверждает доступ к сохранённым учебным ответам. Может отозвать доступ. При отзыве старый использованный код больше не подключит преподавателя заново.
6. Сохранить пробное незаконченное занятие из отдельного ученического аккаунта. Убедиться, что оно открывается у преподавателя; сохранить комментарий и увидеть его у ученика. В другом несвязанном аккаунте отчёт должен быть недоступен.
7. После проверок PostgreSQL и браузерного сценария развернуть интерфейс и проверить реальный авторизованный кабинет. Затем проверить восстановление с другого устройства, повторение ошибок, новую попытку и отзыв доступа при первом подключении ученика. Сохранить резервную ветку для отката интерфейса.

## Ограничения и восстановление

- История старых итоговых баллов сохраняется отдельно в футбольном уроке. Подробные ответы прошлых попыток, которых не осталось в исходном браузере, восстановить по одному баллу или скриншоту нельзя.
- Локальные черновики не гарантируют синхронизацию после закрытия браузера: перед выходом ученик должен увидеть статус «Ответы сохранены в профиле». При сбое ответа данные остаются локально; повтор использует тот же save UUID.
- Одновременная запись устаревшей копии с другого устройства отклоняется с сообщением. История позволяет открыть последнюю версию. Перед восстановлением текущая локальная попытка копируется в ключ с суффиксом `:before-restore`.
- Просмотр страниц ограничен 20 отчётами / 50 учениками, с кнопкой «Показать ещё». Данные загружаются по выбранному ученику, а не целиком по всем ученикам.
- Преподаватель не изменяет исходные ответы ученика. Его заметки хранятся отдельно; RLS проверяет актуальную привязку при каждом чтении.
- Удаление учащегося из `auth.users` удаляет его подробные отчёты и связи каскадно. Обычный сброс урока не удаляет историю.

## Проверки

`npm ci --ignore-scripts`, `npm test`, `node scripts/validate-a1.mjs`, `git diff --check`.

`tests/teacher-db.test.cjs` запускает настоящий PostgreSQL через PGlite: RLS, отзыв доступа, невозможность самоназначения преподавателем, запрет записи в чужую попытку, идемпотентность, конфликты версий и отдельные заметки преподавателя. `tests/teacher-reports.test.cjs` проверяет сохранность первых ошибок, восстановление, ограничение истории, группировку запросов и отмену синхронизации при выходе.
